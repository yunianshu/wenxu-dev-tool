# 一键填报回查误报失败

开始时间：2026-10-14 23:39（Asia/Shanghai）。本次修复提交结果核实与多人任务工时归属，保留现有模块与平台记录保护规则；检索、复现和验证证据集中在本文件，不另建重复的规格文档。

## 现象与证据

- 23:35 的本机提交记录显示：首个禅道任务返回 HTML/脚本响应，`recordEfforts` 回查未匹配，报“无法确认禅道提交结果”；后续任务及汉印没有执行。
- 只读查询确认首个任务的三条工时已经写入，其中长说明由 1732 字符变为 1738 字符，唯一差异是 `<`、`>` 转为 `&lt;`、`&gt;`；另外两条说明及三条记录的工时均与提交载荷相符。凭据、业务说明正文不保存到诊断产物。
- 23:38 的计划把其中一条 0.5 小时记录改绑到了另一任务，原任务从三行变为两行，`submitCore` 因旧记录仍存在而在任何写入前停止。这是有效的残留工时保护，不能简单放开或自动删除平台记录。
- 后续只读查询发现另一目标任务当天已有 6 小时记录属于其他账号。原客户端不检查 `account`，继续提交可能复用该记录。新增隔离复现确认会错误匹配其他账号的记录，需在本次修复中一并纠正。

## 定位与验收

调用链：`fill-service.submitCore` → `ZentaoClient.recordEfforts` → `verifyEfforts` → `getTaskEfforts`。

根因状态：confirmed。`getTaskEfforts` 没有把平台 HTML 转义的工作说明还原为业务文本，`verifyEfforts` 使用原文严格匹配，因此写入成功却中断整批提交。平台只读数据与本机载荷比较直接支持该因果链。

修复范围：在客户端读取边界校验记录账号并仅返回当前账号的记录，单次还原 HTML 特殊字符实体；核实时每条提交必须匹配独立记录，覆盖操作必须匹配指定记录 ID。不得改写提交载荷、递归解码、模糊匹配不同内容或自动重发 POST。

验收：

1. HTML 响应且回查内容仅经过转义时，确认写入并继续后续任务及汉印。
2. 字面实体只解码一层；内容、日期、工时、目标记录 ID 不一致或记录数量不足，仍不能确认成功。
3. 重提复用已有 ID，不重复增加记录；减少行数时仍在写入前拦截。
4. 只读核对真实失败记录；隔离平台验证写入流程，不执行真实工时更新、删除或补交。
5. 共享任务中不复用其他账号的记录，也不借用他人的相同内容确认本次写入；记录缺少账号时停止，不能推定记录归属。
6. 用户明确要求兼容多人任务：单人、多人成员共用提交流程，按“任务 + 日期 + 当前填报账号”匹配；本人未填写时追加，已经填写时覆盖本人记录，不改变共享任务及其他成员的工时。
