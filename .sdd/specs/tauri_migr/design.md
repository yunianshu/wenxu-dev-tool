# 桌面架构迁移设计

## 运行模型

Tauri 承载现有 Vue/Vite 页面和系统窗口。Tauri 启动并监管随包 Node 后台；双方通过带请求 ID 的本机进程消息传输命令、结果和事件。Vue 的 `window.gitReport` API 外观保持不变，由新的浏览器适配层映射到 Tauri 命令和事件。Node 后台保留现有终端、SSH、Git、AI、填报与 Harness 业务模块。原生窗口、目录对话框、剪贴板和本地网页视图由 Tauri 管理。

## 关键决策

- 对应规格 1、4：保持现有前端 API 与业务模块，集中替换 Electron IPC 边界；后台消息按请求 ID 配对，后台崩溃时拒绝在途调用并允许重启。
- 对应规格 2、3：分发与当前 Harness 兼容的 Node 24 运行时及平台原生依赖。Harness 为后台的独立子进程，保留服务状态、端口竞争处理和进程树清理。独立网页视图先验证一次性 token、Strict Cookie、全屏焦点行为。
- 对应规格 5：沿用 `dev-project-manager` 用户数据目录。凭据迁移必须证明现有密文可解密后才切换默认构建；保存旧数据供恢复。Harness 更新保留旧目录直到新服务健康检查成功。
- 对应规格 6：先分别记录轻量版与离线完整版大小，避免将 WebView2 下载和 Harness 下载转移到安装后而误报总占用。

## 验证策略

用现有自测覆盖业务模块；用打包后应用覆盖窗口、终端、Harness 登录/更新和迁移场景；分别构建并核对 Windows/macOS/Linux 安装产物。无法在当前主机运行的平台使用相应 CI 主机验证，未运行的场景保持未完成状态。
