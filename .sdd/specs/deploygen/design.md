# 新项目部署文件生成设计

## 证据与实现模型

当前 `ai-deploy.scanLocal` 的技术栈扫描仅两层，AI 规划/单文件生成主要使用已有部署文件；无部署文件时启发式默认脚本。`auto-deploy.evidence` 已读取部分构建清单，并支持额外补读，但助手未共享。文件写入后界面不刷新部署条件。

- 规则 1/2：增加独立 `project-evidence` 模块，对构建清单、入口、配置及索引限量收集，集中排除运行配置、秘密、链接及同步数据；助手与自动发布复用。AI 最多补读三轮，每轮最多八个路径。
- 规则 3：无既有发布方式时默认 Compose 并请求 Dockerfile/Compose；既有脚本入口保持原推断。提示词根据实际运行时、工作目录、端口和启动入口设计，不凭空发明业务命令。
- 规则 4：增加 `generateFiles(projectId,targetId,plan)`，共享项目证据与方案一次生成完整 JSON 文件集合；截断不采纳，有效结构但校验失败时携带具体反馈修复一次。既有单文件生成附带方案与已生成文件作为参考。
- 规则 5：独立 `deployment-validator` 在虚拟文件集合上检查引用与 Bash 语法，不执行脚本。写入接口附加可选方案以检查整个集合；保留现有备份与写入边界。生成后与写入前重复检查用于阻止未校验内容进入项目。界面写入后重新体检。
- 规则 6：沿用组件 revision，新增互斥状态覆盖批量生成和确认期间；新 IPC 同时接入 Electron preload 与自动生成的 Tauri bridge。
- 规则 7：新增证据、校验、生成链路回归；扩大真实 Vue setup 的上下文回归。构建 renderer，运行相关部署测试，检查两种运行时桥接。

## 决策

生成只修改白名单部署文件；源码问题和外部凭据必须保留为阻塞/配置提示。生成与发布分开，沿用用户在发布页明确点击发布的操作。自动发布已有安全隔离、数据挂载与凭据上传流程继续复用，不建立第二套部署执行器。

默认自动项目的 Compose 方案保留 `executionMode: auto`，套用后仍由自动执行器打包和发布，运行配置不进入 ZIP。内部随机凭据以 Compose 顶层 `x-onedeploy.generatedEnv` 声明，白名单与类型先行校验，再由发布准备阶段生成并复用远端值；`x-onedeploy.healthPath` 将源码证实的健康路径传递给原执行器。外部凭据不会被随机补造。

## 验证边界

真实文件系统、生成文件跨引用、配置持久化和发布编排运行于隔离夹具；AI/SSH 为外部边界。没有指定服务器/项目的生产部署不执行；静态通过、模拟边界编排通过与真实服务可用分别报告。
