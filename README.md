# Personnel PLM

跨平台**Personnel PLM**工作台（Windows / macOS / Linux），基于 Electron + Vue 3。

在本应用中，**项目是一等领域对象**：只填写项目名称即可创建，不要求必须是 Git 仓库，也不要求配置部署。Git 活动、AI 助手和部署都是项目的**可选能力**——Git 只是报告的数据来源之一，而不是产品的中心。

侧栏导航分三组、九个入口：

- **工作区**：工作台、项目
- **项目能力**：AI 助手、DeepSeek Harness、终端工作台、活动报告、一键填报、部署
- **系统**：扩展管理、设置

应用顶部提供统一的当前项目选择器，切换项目后 AI、报告和部署自动使用同一项目上下文。

## 版本更新日志

点击侧栏底部「版本号 · 更新日志」，或进入「设置 → 应用信息」点击「查看更新日志」，即可在弹窗中离线阅读版本记录；支持滚动浏览、关闭按钮和 Esc 关闭，关闭后保留当前页面。

日志统一维护在根目录 `CHANGELOG.md`，构建时自动内置到应用，无需联网或读取本机 Git 仓库。新增改动先写入「未发布」；发布时将相应条目归入实际版本号和日期，并同步 `package.json` 版本。历史目前从 1.4.43 起整理。

## 工作台

进入应用后的默认页面：展示真实的项目数量、当前项目资料完整度、Git 活动状态、部署状态和最近操作，并提供「创建项目 / 询问 AI / 生成报告 / 打开部署」快捷入口。只展示真实数据，不编造指标。启动后台扫描（预热）实时可见：「Git 活动源」卡片随扫描动态计数，并显示扫描进度（已检查目录数）与今日活动加载进度（x/y），完成后恢复为入口态。预热在首帧绘制完成、进入工作台之后才启动，且整个扫描与收集都在独立工作进程内执行（`electron/git-worker.js`），不与首屏渲染抢主进程。

## 项目

项目列表与详情，支持新建、编辑、归档/删除（删除有危险操作确认）：

- 字段：名称、说明、本地目录、状态、标签、项目备注
- 「项目能力」含终端工作台入口：一键切到终端工作台并在分屏窗格中打开该项目的终端
- 「项目能力」含外部终端入口：在项目目录另开一个独立 PowerShell 窗口（macOS/Linux 打开系统默认终端；未关联目录时置灰）
- 「项目能力」含本地调试入口：一键运行项目根目录的 `start.bat`；未找到时提示生成模板（生成后可编辑为实际启动命令），不需要调试的项目可一键关闭并记住偏好
- 只填名称即可创建项目；关联本地目录为可选操作
- 若目录是 Git 仓库则展示 Git 信息，但不改变项目的成立条件
- 已配置部署的旧项目自动出现在项目列表中，原有部署目标与凭据继续可用

## AI 助手

独立的对话工作区，面向整个项目而不只是报告：

- 明确显示当前项目，可勾选上下文来源：**项目资料 / Git 活动 / 报告摘要 / 部署状态**
- 提供「项目总结 / 风险梳理 / 下一步计划 / 生成项目报告」等项目级快捷问题
- 无 Git 数据时仍可基于项目说明和备注对话
- 在「设置 → AI 服务」配置接口地址 / API Key / 模型（支持 OpenAI、DeepSeek、Kimi、通义千问、Ollama 等兼容接口）
- 支持流式输出、停止、复制、保存为 Markdown 文件
- 对话、草稿与生成状态按项目保留；切换项目或页面后，流式回复仍写入发起请求的会话，停止与清空只影响该会话。
- API Key 明文仅存主进程（safeStorage 加密落盘），渲染层仅显示脱敏片段；项目备注、提交文本等外部上下文均按不可信数据处理并受字符预算限制

## DeepSeek Harness（内置 dsh web）

把 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（`dsh` CLI）作为应用内置能力：**打开软件自动开启本地服务，关闭软件自动关闭服务**，无需手动敲命令，**目标机器无需安装 dsh 或 Node**。

- **运行时内置**：安装包内自带固定版本 `@deepseek-ai/dsh` 依赖树，以单个归档 `resources/harness-runtime.tar.gz` 分发，**首次启动解包到用户数据目录 `<userData>/runtime`**（约 30 秒，之后按版本标记复用），由 **Electron 自带的 Node** 执行（`ELECTRON_RUN_AS_NODE=1` + `--expose-internals`；Electron 40+ 内置 Node 24，具备 dsh 需要的 `node:sqlite` 与 `import.meta.main`），目标机器无需安装 dsh 或 Node；首次启动在用户主目录自动生成 `~/.dsh`，离线可用
  - 为什么打成一个归档：依赖树约 2.6 万个文件（217MB），原样放进安装包时 NSIS 要逐文件解压再整树复制，Windows 实测安装需约 16 分钟（用户会以为卡死）；单文件分发后安装约 1 分钟。解包优先用系统 `tar`（约 26 秒），缺失时回退内置 JS 解包器（`electron/harness-runtime.js`）
- **默认配置内置**：首次启动把内置 provider（汉印 `hprt`、智谱 `zai-coding-cn`）与默认模型补进 `~/.dsh/settings.yaml`，目标机器无需手工添加；**不含任何密钥**——只写 `apiKeyEnv` 凭据名，使用者在 Harness「设置 → 模型」填入自己的 key 即可用。只补缺失项，同名 provider 与已有默认模型保持用户原值、注释保留；注入一次后写标记不再改动，settings.yaml 语法错误时原样跳过（`electron/harness-defaults.js`）
- **自动启停**：应用启动时自动拉起 `dsh web`（监听 `127.0.0.1`，默认端口 3080，被占用时自动改用系统分配的空闲端口）；退出应用时连同子进程树一起结束，不留残留服务；异常退出遗留的进程会在下次启动时清理
- **内嵌进入**：侧栏「DeepSeek Harness」直接内嵌完整 Harness GUI（会话、工作区、模型选择、设置），也可一键用系统浏览器打开
- **鉴权闭环**：`dsh web` 就绪后输出的一次性 token 由主进程捕获，内嵌页首次导航用它换取 HttpOnly + SameSite=Strict 登录 cookie 后落到干净根地址——token 不写日志、不落盘
- **状态可见**：页面顶部显示运行状态，底部信息条显示运行时来源（内置 / 本机）、服务地址、PID 与启动时刻；支持「刷新 / 重启服务 / 停止服务」，服务异常退出时展示诊断输出与重试入口
- **服务设置**：端口与「是否随应用自动启动」可配置
- **实现要点**：主进程 `electron/harness-service.js` 负责解析运行时、拉起与整树关闭；渲染层通过 `<webview>`（独立 guest，不受父页 CSP / X-Frame-Options 限制）承载 GUI

运行时解析优先级：已解包的内置运行时 → 本机全局安装的 `dsh` → PATH。开发/调试可用 `DSH_RUNTIME_DIR` 指定运行时目录，或用 `DSH_CLI` 指定可执行文件。

构建：`scripts/prepare-harness-runtime.cjs` 在打包前（`beforePack`）安装固定版本 dsh 到 `build/harness-runtime/`（已缓存，约 217MB，不入库；版本用 `DSH_VERSION` 覆盖），并打成 `build/harness-runtime.tar.gz`（约 49MB）随包分发。安装包体积因此增大（Windows 约 +49MB）。

## 终端工作台（内嵌多窗格终端）

把「多个项目的 CLI 同时盯」做成一个界面：**一个窗格 = 一条终端会话**，四个项目就是上下左右四宫格。

- **内置真终端**：主进程用 `node-pty` 起 ConPTY/pty，渲染层用 xterm.js 显示。不是「另开外部窗口」，命令行、日志与报错都在应用界面里
- **平铺分屏**：最多 4 个窗格，自动按窗格数排布（1 个满屏 / 2 个左右 / 3~4 个 2×2），也可手动锁定「左右 / 上下 / 四宫格 / 三宫格」；窗格之间的分隔条可拖拽调整比例。手动分屏给的是**排布方向**：窗格多于一屏格子时自动往下加行（例如 4 个窗格选「上下」= 竖排 4 行），不会把多出来的窗格挤出可视区
- **同一个项目可以开多个窗格**：一个窗格跑 `npm run dev`、另一个敲 git 是最常见的用法。每个窗格是**独立的 pty 会话**（各自进程与工作目录，输入输出互不串），下拉里会标出该项目已开几个窗格
- **会话常驻**：切到其他页面只销毁终端视图，pty 进程与输出都留在主进程，切回来各窗格认回自己的会话并恢复画面（回放最近 256KB 输出，更早的以「已超出缓冲上限」提示标出）。跑着的 `npm run dev` 不会因为切页被中断
- **多窗口布局记忆**：窗格顺序、每个窗格的标识与绑定项目、shell 选择、分屏方式与列宽行高写入 `userData/terminal-layout.json`，**下次打开软件自动恢复上次的多窗口布局**（进程不跨重启，恢复时按项目目录重新拉起会话；项目被删除或未关联目录的窗格会跳过并提示）
- **shell 解析**：Windows 按 `pwsh` 7 → Windows PowerShell 5.1 → `cmd` 优先级自动选择（与本应用内置 Harness 的解析优先级一致），每个窗格可用标题栏的下拉单独切换；macOS/Linux 用系统默认 shell
- **默认安全**：新建窗格只 `cd` 到项目目录并打开交互式 shell，不自动执行任何命令；窗格内命令以当前用户权限直接运行，不经过 Harness 沙箱与审批
- **入口**：侧栏「终端工作台」；项目页「项目能力 → 终端工作台」可切到工作台并聚焦该项目窗格（原「外部 PowerShell」窗口入口保留）
- **退出即结束**：应用退出时先整树结束 shell 子进程再释放 pty，不留残留进程；会话异常退出（退出码）在窗格上给出状态与「重新打开」入口
- **实现要点**：主进程 `electron/pty-service.js` 管会话表与输出环形缓冲，`electron/terminal-layout.js` 管布局落盘；`node-pty` 是原生模块，通过 `build.asarUnpack` 放在 asar 外，用的是它自带的 N-API 预编译产物（Electron 自带 Node 24 直接加载，无需 node-gyp）
- **打包注意**：`build.npmRebuild` 必须为 `false`——`node-pty` 的 N-API 产物同时兼容 Node 与 Electron，而 electron-builder 默认会调 `@electron/rebuild` 重新编译它，这会在没有 Python/VS 构建链的机器上直接让打包失败（本机实测报 `Could not find any Python installation to use`）。升级 `node-pty` 后请确认 `node_modules/node-pty/prebuilds/<平台>-<架构>/` 里有对应产物

## 活动报告

基于 Git 提交的项目开发报告（Git 是数据源之一，非 Git 项目显示明确空状态并引导使用 AI 基于项目资料整理）：

- 范围：当前项目 / 全部项目
- 周期：日报 / 周报 / 双周报 / 月报 / 自定义起止日期
- 作者：只看本人 / 全部作者 / 指定作者
- 统计卡片 + ECharts 图表（项目提交分布、每日提交趋势）、提交明细按项目折叠
- 报告历史、复制与 Markdown 导出
- 提交统计基于 `git log --all`，默认排除 merge 提交；「本人」身份默认为本机全局 git 身份，可在设置中调整
- 收集前检查仓库 refs/HEAD：拉取、切换或改写引用后立即使历史缓存失效；引用未变时最多复用 120 秒，历史日期也不会永久缓存。

## 一键填报（禅道 + 汉印双平台工时）

基于 Git 提交时间自动计算工时，一次提交同时写入禅道任务工时与汉印工时平台（两个平台各用独立账号）：

- **先生成再勾选**：选好日期与上下班时间后直接点「生成报告」，自动收集**当天所有项目**里你本人的提交并逐项列出（无需先选项目）；随后在明细中勾选要填报的项目（默认全勾选，含未绑定的项目以免工时漏报），**勾选变化会立即按新的项目子集重算工时与汉印占比**（复用已采集的提交，不重复跑 git），未勾选的项目不计入填报；**生成后修改上班/下班时间同样立即按新窗口重算**（工具条预览、明细工时、合计与汉印占比一并跟随，无需再点一次「生成报告」）
- 填写**实际上班时间**（默认取设置页的上班时间，可按天临时调整）：工时与 git 提交时刻完全无关——总工时 = 实际上班时间 → **点击生成报告的时刻**（与填报日期无关，补填历史日期同样按点击时刻；可在工具条手动指定收工时间，早于上班时间按次日跨夜，如 00:30），扣午休后按 0.5 小时整体向下取整；**各项目按当天提交条数占比分配总工时**，且**只要项目当天有提交就保底 0.5 小时**（份额不足半小时不再被抹成 0），余量补给提交最多的项目，保证合计等于总工时（项目多到保底之和已超过总工时时以保底为准，合计会略高于窗口）。一个项目当天合并为一条工时记录，说明为去类型前缀的编号列表（与活动报告「复制」的简洁内容一致）
- **项目绑定禅道任务**：未绑定项目在明细中点「绑定」从禅道任务列表选择——**进行中的排在前面，近一个月内完成/关闭的排在后面**（任务完成后往往还要补填工时，只列进行中会选不到；已取消与超过一个月的不再列出），支持按名称自动建议；绑定一次长期保存在本地（`userData/fill-bindings.json`），之后填报自动关联，无需重复绑定
- 提交前可「预览提交」查看将写入两个平台的完整报文；「一键提交」同时调用禅道 `recordEstimate` 接口写入工时（任务剩余工时自动扣减，最低为 0）与汉印 `workhour/add` 接口提交占比记录
- **重复提交自动转为更新**：提交前查询两平台当日已有记录——禅道按任务查当日已有工时，本次记录复用已有记录 ID（表单键 = effortID 即更新覆盖）；汉印按 `GetByDate` 取当日已填，TaskId 匹配的条目带原 Id 提交（更新占比）；已有但本次未涉及的任务不删除。汇总卡片对已有记录显示「当日已有 N 条 · 将更新」提示
- **覆盖与失败处理**：提交日期必须与禅道、汉印工时行一致，只复用目标日期的记录。禅道剩余工时按「最新剩余 + 本次被覆盖记录的旧消耗 − 本次消耗」计算，最低为 0；重复填报相同工时不会再次扣减。写入前先完成所有相关查询，查询失败停止提交；禅道 HTTP 错误、业务失败或无法确认成功的响应不会显示成功，也不会继续写入汉印。双平台不具备事务回滚，写入中断或结果不明时需先核对平台记录。
- **总量与并发保护**：普通提交、预览和失败重提共用忙状态，主进程拒绝并发执行。取消先前已填报的任务、减少工时行或留下其他汉印占比导致合计不一致时，在写入前列出具体残留并停止；可恢复原项目选择，或在平台核对处理相关记录后重提。现有客户端未提供删除接口，程序不自动删除平台记录。禅道遗漏任务识别依赖本机保留的提交历史；历史被删除或裁剪后，无法发现本次任务列表之外的旧记录。
- 汉印按工时占比填报（**占比为 0% 的条目不会写入**，当日全部条目合计 100%，四舍五入余数补给占比最大的条目）；汉印「软件项目」任务与禅道任务同源，绑定禅道任务后自动匹配汉印任务，未匹配到的任务只写禅道并提示
- 不配置汉印则只填报禅道；生成计划时平台查询失败会提示，提交阶段所涉及平台的查询失败会阻止写入
- 禅道与汉印的地址 / 账号 / 密码在「设置 → 一键填报」分别配置（汉印支持厦门汉印 / 江西外协），密码均经系统安全存储加密落盘；上班时间与午休区间可按需调整
- 支持复制填报报告（明细 + 按任务汇总）到剪贴板留档

## 部署（OneDeploy）

默认使用自动正式发布：**服务器管理中录入一次地址与 SSH 凭据 → 选中项目并选择服务器 → 点击发布**。同一服务器可供所有项目复用，后续项目只需选择，不必重复录入。无需填写远端目录、打包命令或预装本地 Java/Python/Node 构建环境。

- **服务器统一管理**：部署页的「服务器管理」支持新增、编辑和删除未引用服务器；地址、账号及加密凭据只有一份，修改立即用于所有引用项目。被项目使用的服务器会显示引用项目并阻止删除。旧目标的相同连接和凭据自动合并，凭据不同的配置分别保留，不覆盖冲突口令。
- **项目独立配置**：项目保存服务器选择以及独立的安装目录、服务端口、数据库备份、健康检查、数据同步与发布历史。自动模式按稳定项目/目标标识分配目录与端口；高级模式可单独设置安装目录。更改服务器登录信息不会改写项目策略，也不会被旧项目表单覆盖。更换服务器只使该目标的运行探测结果失效，不清除手动设置。
- **按项目备份数据库**：自动模式识别项目 Compose 中唯一明确的 PostgreSQL / MySQL / MariaDB 服务，升级前定位当前运行实例备份，首次没有旧实例时跳过。数据库口令仅在容器内读取。未识别到或存在多个数据库时给出说明，可选择手动配置；每个项目也可明确关闭备份。备份文件位于各项目安装目录，当前一键数据库恢复支持 PostgreSQL。
- **按项目健康检查**：自动模式优先使用本项目 Compose 已有的容器健康检查，否则使用生成方案中的业务 HTTP 接口；也可选择该项目的自定义 HTTP 地址。自动探测结果单独保存，不覆盖自定义地址；关闭 HTTP 探测仍保留容器状态检查。

- 程序识别根目录及子模块，优先使用已有 Compose；缺少可用部署文件时，调用设置中已配置的 AI 自动生成 Dockerfile 与运行方案，可自动补读必要项目文件。生成文件只进入发布快照，不改写源项目。
- 服务器自动复用已有 Docker Compose；缺少环境时在 Ubuntu/Debian 上自动安装 Docker、Compose、解压与校验工具。构建在服务器容器内完成。每次发布重新打包当前代码；构建失败时把脱敏错误交给 AI 修复并重试一次，构建期间旧服务继续运行。
- 每个项目、正式目标使用独立目录、Compose 项目名、服务端口与持久化数据卷。版本目录和构建镜像按发布记录区分，同版本代码更新也不会覆盖回滚镜像。历史回滚使用发布实例 ID，兼容旧版本记录。容器检查与该项目启用的业务 HTTP 检查通过才记为成功。
- 内部数据库口令、应用密钥自动生成并在后续版本复用；外部 API 密钥无法推定，缺少时明确列出需要在项目 `.env` 中填写的变量。运行凭据通过 SSH 单独上传并限制文件权限，不进入 AI 提示、发布 ZIP 或 Docker 构建上下文。
- 已有 Compose 的 `env_file` 按声明的顺序、可选项和格式保留，通过 SSH 上传为发布实例专属副本，回滚使用对应版本的配置。任意文件名的运行配置同样排除于发布包和构建上下文。
- 新项目不再继承上个项目的版本、构建脚本或远端目录。「从其他项目复制」只追加服务器引用。已有脚本/Compose 部署继续保留，在「部署设置」中可切换自动发布。

以下为通用流程及高级部署能力：版本识别 → 打包 → 上传 → 服务器备份 → 解压 → Docker 构建 → 重启 → 健康检查，失败时尝试恢复旧版本。代码回滚不回退数据库结构或业务数据；已有生产实例接管、数据迁移和自定义数据库备份使用高级设置与 AI 部署助手。

- 以全局当前项目为输入；一个项目可配置多个部署目标（测试 / 生产 / 多台服务器），每个目标选择共享服务器，独立保存远程目录、健康检查与数据配置
- 服务器、健康检查、备份等低频配置收进「部署设置」面板，首屏只保留发布状态、主要动作、阶段进度、日志和历史
- **数据同步（按项目与目标）**：把本地数据目录（如 `data/`）打包上传，解压覆盖到当前项目目录内（默认 `shared/data`，跨版本共享），上传经 SHA256 校验。自动发布中直接挂载给容器的数据在备份、构建通过后、启动新版本前同步，首次启动即可读取；仅用导入命令处理的数据和高级模式仍在发布成功后同步。同步失败会停止后续步骤并报告实际状态；代码回滚不会撤回已同步文件或导入的业务数据。不同项目、生产与测试分别启用和配置。
- **同步归属检查**：本地数据限定在当前项目内，远端限定在当前项目安装目录内；上传前和解压前检查目录，拒绝目录联接、符号链接及硬链接。自动模式将匹配的数据目录挂载绑定到该项目共享目录；没有匹配的容器挂载且未配置导入钩子时，先说明缺少的数据用途并停止，避免文件同步成功但应用无法读取。
- **同步后导入钩子**：数据同步完成后可在服务器上执行一条导入命令（占位符 `{dataDir}` 远端数据目录、`{user}`/`{secret}` 应用账号凭据，密码加密存储不出主进程），用于把同步的数据调用应用自身接口写入其数据库——例如 PrinterManager 的 `deploy/import-products.sh` 登录应用后调用 JSON 导入接口完成产品入库；导入失败整单标记失败
- **版本号自动识别**：按 `VERSION` → `package.json` → `pom.xml` → `build.gradle(.kts)` → `pubspec.yaml` → `*.csproj` 优先级读取，也可手动指定
- **智能打包**：自动排除 `.git`、`node_modules` 等目录，Docker 发布保留可能被 Dockerfile 引用的 `dist`、`build`、`target`；支持项目根目录 `.deployignore` 自定义忽略与 `!` 重新包含规则，上传后 SHA256 校验。脚本模式配置打包命令后每次重新构建，版本同步与发布说明只写入临时构建副本；支持嵌套产物目录和精确版本匹配，上传前检查发布包结构与升级入口。
- **服务器目录规范**（`<部署目录>` 下，可自定义根）：

  ```
  <部署目录>/
  ├── current -> releases/<version>   # 软链接指向运行版本
  ├── releases/  uploads/  backups/  shared/  deployer/
  ```

  自动模式根目录为 SSH 用户目录下 `.onedeploy/apps/<项目目标标识>`，`shared/.env` 以权限受限的副本进入各版本，镜像版本号固定在各自 Compose 中；高级 Compose 模式共享配置保留原软链接行为。
- **发布流程 9 阶段可视**：检查项目 → 项目打包 → 上传文件 → 备份服务器 → 解压新版本 → Docker 构建 → 启动服务 → 健康检查 → 数据同步（未启用时显示跳过）
- **安全防护**：发布锁防并发、防重复点击、上传包校验、健康检查失败/连接中断自动回滚
- **健康检查**：HTTP 探测（如 `/actuator/health`），未配置时检查容器运行状态；可选 PostgreSQL / MySQL 数据库备份
- **发布历史与回滚**：记录每次发布（状态/耗时/失败原因/完整日志），支持从历史版本一键回滚
- **本次更新内容**：发布时自动读取同一项目、同一部署目标上一次成功发布到本次提交之间的 Git 记录，已知版本范围不限制提交条数；没有历史时取最近可达标签，都没有则收录最近 60 条。发布和可选数据同步全部成功后，自动在本地仓库创建 `v版本号` 标签并写入历史，下次据此确定更新范围；失败、取消或回滚不自动打标。同名标签仅在指向相同提交时复用，冲突不覆盖，原因写入部署日志和历史字段，已完成的部署仍记为成功。标签不会自动推送远端。发布成功后由 AI 整理成通俗中文说明，AI 不可用时退回本地整理；历史中「查看」可看说明与原始提交，也可手动补标签。Git 标签仅记录提交，未提交改动及外部成品包内容不在 Git 更新说明中。
- **数据库备份恢复**：开启「发布前备份数据库」的项目，发布页可查看服务器上的全部 pg_dump 备份并一键恢复——恢复前自动保底备份当前库（失败即中止），随后杀连接重建空库、灌入选中备份（出错即停）、重启同 Compose 项目容器；恢复记录（类型「数据恢复」）与完整日志进入发布历史
- **凭据安全**：SSH 密码/私钥口令经 safeStorage 加密落盘，明文不保存、不出主进程

### AI 部署助手（高级接入与已有实例接管）

自动正式发布会自行完成首次项目分析与部署文件准备，无需逐个生成文件。需要接管旧实例、自定义部署或迁移数据时，部署页右上角「AI 部署助手」提供：

1. **项目体检（本地）**：技术栈标记、版本来源、部署文件清单（Dockerfile / Compose / 打包与升级脚本 / `.env.example`）、发布产物目录、运行时数据目录候选、敏感文件；缺什么直接列出。
2. **部署条件校验（服务器）**：SSH 探测 Docker / Compose / unzip / tar / curl / sha256sum / java / pg_dump、磁盘与内存、部署目录现状与受管指针（`CURRENT` / `releases`）、`docker compose ls` 项目、同名容器与数据卷、Compose 声明端口的占用情况。
3. **已有部署识别（确定性）**：给出 `managed`（本工具部署过）/ `legacy`（手工或其他方式部署）/ `content` / `empty` / `none` 判定与逐条证据；`legacy` 时给出「备份 → 迁移可变数据到 `shared/` → 停旧实例（保留具名卷）→ 清理目录 → 首次发布」的接管步骤，并点名**必须原样保留**的东西（数据卷名、共享目录、Compose 项目名）。
4. **AI 方案**：把两份体检 + 部署契约交给已配置的模型，产出部署形态（脚本 / Compose）、脚本模式、版本策略、健康检查、数据库备份、数据同步结论、缺失文件、首次部署前置条件与风险；AI 不可用时自动降级为确定性规则结论（界面标注结论来源）。
5. **生成 / 改写部署文件**：AI 指出需要新增或改写的部署文件（例如把只认 `--install-root` 的 `upgrade.sh` 改写为从 `INSTALL_ROOT` 环境变量取安装根），逐个「生成内容」→ 预览 → 写入；只允许部署相关文件（Dockerfile、compose、`.env.example`、根目录或 `deploy/`、`scripts/` 下的 `*.sh`、`migrations/*.sh`），写入前自动把原文件备份为 `*.bak-<时间戳>`。
6. **套用到部署配置**：一键把方案写回该项目的部署形态 / 脚本模式 / 版本 / 健康检查 / 数据库 / 数据同步（不改动服务器地址与凭据）。

**数据同步结论的口径**：方案区分两种常被混为一谈的情况——`share`（数据由服务器自己产生，只需迁移到 `<安装根>/shared` 跨版本共享，**不需要**把本地数据推上去）与 `upload`（本地有服务器不会自己产生的数据，需要随发布推送）。只有后者才建议启用「数据同步」。

**助手安全边界**：读写部署文件拒绝经过符号链接或 Windows junction；连续覆盖各自保留独立备份。诊断与单文件生成发送前会隐藏常见密码、Token、私钥、带密码 URL 和命令行凭据（规则脱敏无法识别任意无标记的秘密，凭据仍应放在环境变量或独立 secret 文件中）。项目、环境、目录切换或关闭助手会清空方案，旧异步结果和旧确认框不能写入新上下文。部署条件按最终形态及确定性证据重算，AI 空清单不能消除服务器、版本或文件缺失。每个数据目录必须标明 `share` / `upload`；现有配置仅支持一个上传目录，多目录或用途不明时拒绝整次套用并提示手动选择。

**AI 结构化输出**：方案走非流式接口并要求 `reasoning_effort=none`——推理型模型在流式下会把输出预算全用在推理上导致正文为空；网关不支持该参数时自动去掉重试。输出被长度上限截断时，工具会回退到「只要方案 + 文件清单」，并把截断半截的文件内容整条丢弃（绝不写入半截脚本）。

### 部署服务器要求

- 自动正式发布：可通过 SSH 登录的 Linux，首次安装环境需 root 或免密 sudo；当前自动安装支持 Ubuntu/Debian，其他 Linux 可复用已有 Docker Compose。服务器需能下载依赖和镜像，云安全组应允许访问最终服务端口（程序不改动云账户规则）。
- 高级 Compose 模式：预装 Docker、**Docker Compose V2**、`unzip`、`sha256sum`、`curl`，项目提供 Dockerfile 与 Compose 文件。
- 缺少部署文件的自动模式需要已配置可用 AI；有可直接使用的 Compose 时不要求 AI。自动化不保证任意不完整项目可运行；外部业务凭据、SSH 权限和服务器网络限制无法由程序凭空补齐。
- **脚本部署契约**（项目自带运维脚本时）：发布包为 `.tar.gz`/`.tgz`/`.zip` 且只含单一顶层目录、文件名含版本号；工具解压为 `<安装根>/releases/<顶层目录名>/` 后以「当前目录 = 该 release 目录」执行 `bash ./upgrade.sh`（只传环境变量 `INSTALL_ROOT=<安装根>`，不传参数）；版本指针 `<安装根>/CURRENT`（内容 = release 目录名）由工具维护，发布成功后写入，回滚与「线上版本」查询都读它；发布包内必须有 `VERSION` 与 `start.sh`
- 服务器端逻辑集中在 `deploy.sh`，由客户端自动上传，无需手工布置

- **技能启停**：采用目录迁移法（`skills/` ↔ `skills-disabled/`），与 Codex 官方禁用机制一致，可逆且不改动各 CLI 自身文件；链接技能（如 Zcode 聚合层指向 Claude Code 的 junction/symlink）启停时**级联同步源平台**——禁用会连同源平台真实目录一起移入禁用位，启用时先恢复源目录再重建链接，失败自动回滚；指向外部目录的链接仅移动链接本身；源平台直接禁用导致的悬空链接会在列表中标记「链接失效」，仍可开关处置
- **插件启停**：直接写入各平台自身的启用配置——Claude Code 写 `~/.claude/settings.json` 的 `enabledPlugins`，Zcode 写 `~/.zcode/cli/config.json` 的 `plugins.enabledPlugins`，Codex 定向翻转 `~/.codex/config.toml` 对应 `[plugins."id"]` 段（保留其余内容与换行风格）；Kimi CLI 暂无插件体系时明确提示
- **安全边界**：配置文件解析失败时拒绝写入并保留原文件；技能/插件名称做路径穿越校验；同名冲突时拒绝覆盖

## 打包发布

```bash
npm run build:renderer  # 仅构建渲染层到 dist/
npm run build:win       # Windows（NSIS 安装包 + 便携版）
npm run build:mac       # macOS（dmg）
npm run build:linux     # Linux（AppImage + deb）
```

产物输出至 `release/` 目录（每个版本约 758MB：安装包 + 便携版 + win-unpacked）。
本地更新通道（`npm run install:local` / `update:local`）安装成功后会**自动清理
`release/` 下的旧版本目录**，只保留当前版本，避免逐版本累积占满磁盘。需要单独清理时：

```bash
node scripts/prune-releases.cjs --dry-run  # 先看将删除哪些（不动文件）
node scripts/prune-releases.cjs            # 执行：保留 package.json 当前版本，删除其余版本目录
```

## 数据存储

- 项目数据与配置保存在 `userData/config.json`、`userData/deploy-projects.json`（兼容旧部署项目数据；后者同时存储共享 `servers` 和项目目标的 `serverId` 引用）
- 一键填报的项目-禅道任务绑定保存在 `userData/fill-bindings.json`
- 内置 Harness 服务的进程记录保存在 `userData/harness.json`（用于清理异常退出遗留的服务进程）
- 终端工作台的多窗口布局保存在 `userData/terminal-layout.json`（独立于 `config.json`，避免被「保存设置」的整体回写覆盖）
- 发布历史保存在 `userData/deploy-history.json`（完整日志在 `userData/deploy-logs/`）；每条发布记录同时保存本次采集到的 Git 提交号、采集范围、提交列表与更新说明
- API Key、SSH 凭据与禅道/汉印密码经 safeStorage 加密落盘

## 说明

- Git 活动采集只需本机安装 git，无需联网；未安装 git 或项目不是 Git 仓库不影响项目、AI 助手等其他能力的使用。
- 首次使用报告能力时若检测不到全局 git 身份，请在「设置 → 个人身份」确认本人姓名/邮箱，或在系统中配置 `git config --global user.name/email`。
- 部署能力需可访问目标服务器（SSH 22 或自定义端口）；数据卷请挂载到 `shared/` 或绝对路径，避免放入版本目录随发布被清理。
